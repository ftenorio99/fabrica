# ADR 0015: Dispatcher no GitHub Actions pelo CLI, em runner do GitHub, com a assinatura

**Status:** aceito · **Data:** 2026-11-18 · **Origem:** issue #99

## Contexto
A F4 do [PRD](../prd.md) pede que aplicar `agente` numa issue dispare a etapa de agente no GitHub Actions, com o plugin instalado no job e sem sessão local. O PRD impõe quatro requisitos que pesam aqui: **um fluxo só** (as mesmas skills no terminal e no Actions, com o estado só no GitHub), **concorrência** (uma execução por issue), **sem cascata** (só os gestos do usuário disparam) e a **ordem** (o isolamento da F1 e as credenciais da F2 vêm antes do dispatcher). Duas perguntas em aberto do PRD, o runner e a autenticação, ficaram para este estudo, e o risco de alto impacto "a assinatura não permite uso automatizado no Actions" manda conferir os termos antes de escolher.

O `/fabrica:avancar` já roda cada etapa num `claude -p` próprio pelo `scripts/stage-model.sh run`, que escolhe o modelo pela etapa e pela label `modelo:*` ([ADR 0013](0013-modelo-por-etapa-e-por-issue.md)). Os comentários do agente e do usuário saem da mesma conta do GitHub e se distinguem pelo marcador `<!-- fabrica:` ([estados.md](../../skills/status/estados.md)).

Esta ADR decide o caminho de execução, o runner, a autenticação e o disparo. O workflow é a #105, o isolamento do job é a #106 e a instalação pelo `/fabrica:setup` é a #108.

## Fatos conferidos

## Decisão
- **D1 — Caminho de execução: o CLI direto no job, chamando a mesma `bash scripts/stage-model.sh run <etapa> <nº> [label...]` do `/fabrica:avancar`.** O job instala o CLI e o plugin com `claude plugin marketplace add ftenorio99/fabrica` e `claude plugin install fabrica@fabrica`, e o `stage-model.sh` escolhe o modelo da etapa pela ADR 0013. A `claude-code-action` não é usada.
- **D2 — Runner: o hospedado pelo GitHub (`ubuntu-latest`) no M2.** O self-hosted na Hetzner fica para quando os minutos ou o tempo de fila medidos pelo `/fabrica:metricas` pedirem.
- **D3 — Autenticação: a assinatura, com o `CLAUDE_CODE_OAUTH_TOKEN` gerado por `claude setup-token` e guardado como secret do repositório.** A fonte oficial permite o uso automatizado de forma explícita (tabela acima). O `--max-budget-usd` não vale com a assinatura, porque só limita gasto em chamadas de API; o teto de cada execução é o `timeout-minutes` do job e o limite de uso da própria assinatura. A API key (`ANTHROPIC_API_KEY`) com `--max-budget-usd` por execução continua como plano B, se os termos mudarem ou se o dispatcher passar a servir mais de uma pessoa.
- **D4 — Disparo: evento `issues` com `types: [labeled]` e filtro `github.event.label.name == 'agente'`, com grupo de concorrência por issue** (ex.: `group: fabrica-${{ github.event.issue.number }}`).
- **Escritas do job:** comentários, labels, push e PR saem com o `GITHUB_TOKEN` do job no M2, que a #106 troca pelo token fine-grained. Os eventos do `GITHUB_TOKEN` não disparam workflows, e o filtro da D4 é a segunda trava (ver "Sem cascata").
- **Headless:** o job roda o `claude -p` em `auto`, que é o que o `stage-model.sh` escolhe fora da VM do sbx ([ADR 0013](0013-modelo-por-etapa-e-por-issue.md)). Não há `--max-turns` na versão 2.1.327, então não há teto de turnos.

### Comparação dos caminhos de execução
| Opção | Instala o plugin | Escolhe o modelo da etapa (ADR 0013) | Comentário fora dos marcadores |
|---|---|---|---|
| Action com `label_trigger`, modo interativo | Pelos inputs `plugin_marketplaces` e `plugins` | Não sabe da tabela: o modelo iria fixo em `claude_args`, ou a action chamaria o `stage-model.sh` dentro de outro Claude | Sim: cria o próprio comentário de acompanhamento, sem `<!-- fabrica:`, que o `/fabrica:status` trataria como comentário do usuário (resposta nova) |
| Action com `prompt`, modo de automação | Pelos mesmos inputs | Repete a escolha em `claude_args` (`--model`), fora do `skills/avancar/modelos.md`, ou exige um passo anterior que chame o `stage-model.sh model` | Não por padrão (só com `track_progress`), mas escreve com o token do App da Anthropic, salvo com `github_token` |
| **CLI pelo `stage-model.sh run` (escolhida)** | `claude plugin marketplace add` e `claude plugin install` num passo do job | Sim, pelo mesmo `stage-model.sh` do `avancar`, sem duplicar a tabela | Não: só a skill comenta, com os marcadores dela |

### Comparação dos runners
| Critério | Hospedado pelo GitHub (`ubuntu-latest`, escolhido) | Self-hosted na Hetzner |
|---|---|---|
| Custo no piloto | Sai do valor mensal do plano (cerca de 2.000 min no Free e 3.000 no Pro a US$ 0,006/min). Uma etapa de 10 a 20 min cabe com folga num piloto de poucas issues por semana. | O servidor é pago todo mês, use ou não; o minuto do Actions não é cobrado em runner self-hosted. |
| Manutenção | Nenhuma: o GitHub atualiza a imagem. | Atualizar o sistema, o runner e as ferramentas, e acompanhar a máquina. |
| Máquina descartada a cada job | Sim: cada job ganha uma VM nova, o que já cumpre parte da F1 (nada fica de um job para o outro). | Não por padrão: precisa de runner efêmero (`--ephemeral`) com limpeza ou de um contêiner por job, antes do primeiro job. |
| Rede (a cargo da #106) | A VM sai para qualquer host; a #106 restringe por dentro do job (proxy ou firewall com a lista de domínios liberados, ou o `sbx` no runner, se couber). | A #106 restringe no firewall da máquina, mas também precisa isolar um job do outro e do próprio servidor. |

### Sem cascata
- **Quem escreve:** todas as escritas do job (comentários, labels, push e PR) usam o `GITHUB_TOKEN` do job no M2. A #106 troca pelo token fine-grained e precisa preservar a propriedade abaixo.
- **Se os eventos disparam:** os eventos do `GITHUB_TOKEN` não disparam workflows (tabela acima). Uma label aplicada pela etapa (`em-andamento`, `spec-pronta`, `escalonado`) não dispara o workflow de `labeled`.
- **Filtro:** o workflow só roda em `issues: labeled` com `label.name == 'agente'`, e `agente` só é aplicada pelo usuário (tabela de labels de [estados.md](../../skills/status/estados.md)). Como agente e usuário usam a mesma conta, o autor do evento não serve de filtro: o que distingue é o nome da label e, para os comentários da retomada (#107), o marcador `<!-- fabrica:` na primeira linha. Se a #106 trocar o `GITHUB_TOKEN` por um token que dispara workflows (PAT ou App), o filtro passa a ser a única trava e precisa continuar ignorando as labels das etapas e os comentários com marcador.
- **Efeito no CI do PR:** o push e o PR feitos com o `GITHUB_TOKEN` não rodam o CI direto: o `pull_request` `opened` ou `synchronize` fica esperando aprovação manual no Actions. O PR do agente chega sem CI verde até o usuário aprovar o run, e o `revisar` não vê a assinatura de CI do PR. A #105 decide o caminho: aceitar a aprovação manual no piloto, ou disparar o CI por `workflow_dispatch` depois do push, que é a exceção à regra.

### Headless
- **Modo de permissão:** `auto`, o que o `stage-model.sh` já devolve no runner (não há VM do sbx). O `bypassPermissions` só entra se a #106 rodar o job dentro do `sbx`, com a mesma regra da ADR 0013.
- **Quando o `auto` aborta sem usuário:** o `claude -p` termina com erro e não há quem responda. A etapa falha, a `em-andamento` fica na issue até expirar em 2 h ([ADR 0003](0003-sinal-de-etapa-em-andamento.md)), e o job precisa publicar o motivo na issue num passo final (`if: failure()`), a cargo da #105. O `auto` já bloqueou a `spec` no `-p` do host em 3 de 3 execuções (ADR 0013): a #105 confere esse caso no repositório de teste antes de ligar o dispatcher num projeto.
- **Teto de turnos:** o `claude --help` 2.1.327 não tem `--max-turns`. O teto de cada execução é o `timeout-minutes` do job e, com a assinatura, o limite de uso dela. Com a API key do plano B, entra também o `--max-budget-usd`.

## Alternativas consideradas
| Alternativa | Por que não |
|---|---|
| `claude-code-action` com `label_trigger` (modo interativo) | Cria o próprio comentário de acompanhamento, fora dos marcadores `<!-- fabrica:` que o `/fabrica:status` lê, e não sabe da tabela de modelos da ADR 0013. |
| `claude-code-action` com `prompt` (modo de automação) | Funciona, mas repete a escolha de modelo em `claude_args`, fora de `skills/avancar/modelos.md`, e por padrão escreve com o token do App da Anthropic, que a #106 trocaria pelo token fine-grained de qualquer forma. É uma camada a mais sobre o mesmo CLI. |
| Self-hosted na Hetzner já no M2 | Exige manter a máquina, limpá-la entre jobs e isolar o runner antes do primeiro job; o ganho de custo só aparece com volume que o piloto ainda não tem. |
| API key com `--max-budget-usd` como escolha principal | Os termos permitem a assinatura de forma explícita, e a fábrica já roda na assinatura (ADR 0013); a API key cobraria à parte o que a assinatura já cobre. Fica como plano B. |
| Assinatura sem conferir os termos | O risco de alto impacto do PRD proíbe; a conferência está na tabela "Fatos conferidos". |
| Disparo pelo `label_trigger` da action | Está preso ao modo interativo, descartado na D1. |
| Entregar já um workflow de exemplo | Invade a #105; este item do fatiamento é só o estudo com a ADR. |

## Consequências
- **#105 (workflow):** dispara só em `issues: labeled` com `github.event.label.name == 'agente'`, com `concurrency` por número da issue; roda em `ubuntu-latest` com `timeout-minutes`; instala o CLI e o plugin (`claude plugin marketplace add ftenorio99/fabrica` e `claude plugin install fabrica@fabrica`) e chama `bash scripts/stage-model.sh run <etapa> <nº> <labels...>` do plugin instalado; lê o secret `CLAUDE_CODE_OAUTH_TOKEN` (ou `ANTHROPIC_API_KEY` no plano B, com `--max-budget-usd`); aplica e remove a `em-andamento` (ADR 0003); publica o motivo da falha na issue num passo `if: failure()`; decide como o CI do PR do agente roda (aprovação manual ou `workflow_dispatch`); confere no repositório de teste se o `auto` deixa a etapa terminar no runner; e reconfere os fatos desta ADR.
- **#106 (isolamento do job):** entra entre a instalação e o `stage-model.sh run`: restringe a rede da VM à lista de domínios liberados (inclusive a API da Anthropic, o GitHub e o marketplace do plugin), troca o `GITHUB_TOKEN` pelo token fine-grained com as permissões mínimas (issues, pull requests e contents do próprio repositório) e mantém o secret de autenticação fora do alcance de leitura do agente (F2). Se o token novo disparar workflows, o filtro da D4 precisa continuar barrando as labels das etapas e os comentários com marcador. Se ela rodar o job dentro do `sbx`, o modo vira `bypassPermissions`, pela regra da ADR 0013.
- **#108 (instalação pelo `/fabrica:setup`):** copia o workflow para `.github/workflows/` do projeto e orienta o usuário a gerar o token com `claude setup-token` e cadastrar o secret `CLAUDE_CODE_OAUTH_TOKEN` no repositório, como ação externa ([ADR 0012](0012-acao-externa-com-checklist.md)); o guia cita o plano B da API key.
- **#107 (retomada por evento):** reusa o mesmo filtro por nome de label e por marcador na primeira linha do comentário, porque o autor do evento não distingue agente de usuário.
- A linha de custo funciona no job: o `stage-usage.py` lê o log da sessão do próprio runner, gravado pelo `claude -p` durante a execução. O log some com a VM; a métrica persistente é a F9, que pode usar a `CLAUDE_CODE_ENABLE_TELEMETRY`.
- O token da assinatura vence em um ano e fica preso à conta de quem o gerou; renová-lo é uma ação externa do usuário.
- A conta do usuário gasta o limite de uso da assinatura também com os jobs; se ele apertar, os minutos do runner e o limite de uso medidos pelo `/fabrica:metricas` dizem se vale trocar para a API key ou para a Hetzner.
