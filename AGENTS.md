# AGENTS.md

Este repositório é a fábrica de software pessoal, empacotada como plugin do Claude Code. Mudar a fábrica é abrir um PR aqui.

As regras de git, idioma e segredos do projeto estão em `templates/AGENTS.md` e valem aqui também.

## Estrutura
- `.github/workflows/ci.yml`: workflow de CI do próprio repositório; roda as suítes unitárias `scripts/test-*.sh` (exceto os testes de aceite `test-job-acceptance.sh` e `test-sandbox-acceptance.sh` e o eval sob demanda `test-revisor-quality.sh`) em `pull_request` e `push` na `main`.
- `.claude-plugin/plugin.json`: identidade do plugin. Suba a `version` a cada mudança que altere comportamento.
- `.claude-plugin/marketplace.json`: permite instalar o plugin com `/plugin marketplace add ftenorio99/fabrica`.
- `skills/<nome>/SKILL.md`: uma skill por etapa do fluxo. No uso, são chamadas como `/fabrica:<nome>`.
- `skills/etapas/regras.md`: as regras comuns às etapas (corpo por arquivo, plano B do `gh`, label inexistente, marcador dos comentários e linha de custo). A pasta não tem `SKILL.md`, para não virar comando.
- `agents/`: subagentes usados pelas skills (ex.: revisor), lidos pelo Claude Code e pelo OpenCode. O Antigravity (`agy`) lê o revisor de `agy-agents/revisor.md`, declarado no `agents.json` da raiz: o mesmo corpo, com os nomes de ferramenta do `agy`.
- `githooks/`: hooks globais do git que recusam commit e push na `main`, instalados por `scripts/setup-githooks.sh` (ADR 0002).
- `hooks/`: hooks do Claude Code que valem onde o plugin estiver instalado (ex.: `protect-main.sh`, que impede o Claude de desligar os hooks do git, e `protect-production.sh`, que recusa comandos com padrões de produção). Esses dois também aceitam a entrada do `PreToolUse` do Antigravity e respondem no formato dele, para a conversão do `agy plugin install` não deixá-los sem efeito. O `session-start.sh`, que avisa quando os hooks do git não estão instalados, faz o mesmo com o `SessionStart` (texto puro no Claude Code, `injectSteps` no Antigravity).
- `scripts/`: scripts chamados pelas skills (ex.: `setup-labels.sh`, `setup-githooks.sh`). Os testes da proteção da main rodam com `bash scripts/test-protect-main.sh`, os da statusline com `bash scripts/test-statusline.sh`, os do modo de isolamento com `bash scripts/test-setup-isolation.sh`, os das regras comuns das etapas, que ficam só no arquivo comum, com `bash scripts/test-regras-etapas.sh`, os do contexto do checklist do `sbx` com `bash scripts/test-sbx-context.sh`, os do bloqueio de produção com `bash scripts/test-protect-production.sh`, os do aviso do `SessionStart` com `bash scripts/test-session-start.sh`, os do `acao-status.py`, que lê a checklist da ação externa, com `bash scripts/test-acao-status.sh`, os do `stage-model.sh`, que escolhe o modelo de cada etapa e roda o `claude -p`, com `bash scripts/test-stage-model.sh`, os da detecção de harness pelo `harness.sh`, que decide entre o modelo da sessão e o `claude -p`, com `bash scripts/test-harness.sh`, e os do `issue-worktree.sh`, que cria, reusa e limpa a worktree de cada issue em `<clone>/.worktrees/<nº>` ([ADR 0014](docs/adr/0014-uma-worktree-por-issue.md)), com `bash scripts/test-issue-worktree.sh`, os dos dois arquivos do revisor (`agents/revisor.md` e `agy-agents/revisor.md`, com o corpo igual) e do `agents.json`, com `bash scripts/test-revisor-agent.sh`, os dos campos de frontmatter das skills (`disallowed-tools` no `avancar`, `context: fork` e `effort: medium` no `status` e no `metricas`, `effort: medium` no `setup` e nenhum deles nas etapas de julgamento), com `bash scripts/test-skill-frontmatter.sh`, e o eval sob demanda do subagente `revisor` contra uma branch com 3 defeitos plantados e uma branch de controle limpo, que roda fora do CI (para não consumir tokens) com `bash scripts/test-revisor-quality.sh`, e os do `dispatch.sh`, que o workflow do dispatcher chama a cada gesto do usuário para rodar as etapas no GitHub Actions, junto com os do próprio workflow, com `bash scripts/test-dispatch.sh`, e os do `issue-state.py`, o leitor da tabela de estados que o `dispatch.sh` usa para escolher a etapa ([ADR 0017](docs/adr/0017-leitor-de-estado-em-codigo-para-o-dispatcher.md)), com `bash scripts/test-issue-state.sh`, e os do `setup-dispatcher.sh`, que o `/fabrica:setup` usa para conferir e instalar o workflow do dispatcher no projeto, com `bash scripts/test-setup-dispatcher.sh`, e os do `setup-ci.sh`, que o `/fabrica:setup` usa para conferir e instalar o CI do PR no projeto, junto com os do modelo `templates/workflows/ci.yml`, com `bash scripts/test-setup-ci.sh`, e os do `publish-screenshots.sh`, que o `revisar` usa para gravar os screenshots das telas na branch órfã `fabrica-telas` do projeto ([ADR 0020](docs/adr/0020-screenshots-das-telas-numa-branch-orfa.md)), com `bash scripts/test-publish-screenshots.sh`, e os do `ci-wait.sh`, que o `revisar` usa para esperar o CI do PR, com `bash scripts/test-ci-wait.sh`. Os testes do `base-drift.sh`, que o `revisar` e o `status` usam para saber se a `main` avançou em arquivos de um PR ou se há conflito, rodam com `bash scripts/test-base-drift.sh`. O isolamento do job do dispatcher fica no `job-isolation.sh` (usuários, lista de domínios com os hosts do `.fabrica/dominios.txt` do projeto, proxy e regras de rede; [ADR 0018](docs/adr/0018-lista-de-dominios-por-projeto.md)), no addon `egress-addon.py` do `mitmdump` (lista de domínios, troca do marcador pelo segredo e push para a `main` barrado; [ADR 0021](docs/adr/0021-push-na-main-barrado-pelo-proxy-do-job.md)) e no `run-as-agent.sh` (roda o `claude` como o usuário sem rede direta); os testes rodam com `bash scripts/test-job-isolation.sh`, e o `scripts/test-job-acceptance.sh`, que roda só no runner, é o teste de aceite do isolamento do job ([ADR 0016](docs/adr/0016-isolamento-do-job-do-dispatcher.md)). O `migrate-native-sandbox.sh` remove os restos do sandbox nativo, que saiu da fábrica ([ADR 0010](docs/adr/0010-isolamento-pelo-sbx-com-opcao-sem-sandbox.md)), e os testes dele rodam com `bash scripts/test-migrate-native-sandbox.sh`. O `scripts/test-sandbox-acceptance.sh` é o teste de aceite do isolamento e roda dentro da VM do `sbx`.
- `opencode/`: adaptador da fábrica para o OpenCode, com as skills, os comandos `/fabrica:*`, o subagente `fabrica/revisor` e os hooks de proteção; a instalação e os limites estão em `opencode/README.md`. O teste de aceite roda com `bash opencode/test-adapter.sh`, dentro da VM do `sbx` com o agente `opencode`.
- `docs/`: manual de uso da fábrica (`docs/README.md` é o índice) e ADRs em `docs/adr/`.
- `templates/`: arquivos copiados para os projetos (`AGENTS.md`, com as regras do projeto, `CLAUDE.md`, que importa o `AGENTS.md`, `design.md`, issue, spec). O `design.md` é o formato do design system de um projeto com interface, copiado pela primeira spec com interface. Em `templates/workflows/` ficam o workflow do dispatcher (`agente.yml`), que o `/fabrica:setup` copia para `.github/workflows/` do projeto, o modelo do CI do PR (`ci.yml`), que o `/fabrica:setup` instala num projeto sem CI e nunca sobrescreve ([guia](docs/guias/ci-do-pr.md)), o do teste de aceite do isolamento (`isolamento-aceite.yml`), copiado à mão só para o repositório de teste, e a lista de domínios liberados ao agente (`dominios-liberados.txt`), que o job lê do plugin instalado e não é copiada ([guia](docs/guias/dispatcher.md)).

## Escrevendo skills
- O texto da skill é instrução para o Claude: imperativo, direto, em português.
- O `description` do frontmatter diz o que a skill faz e quando usar; é ele que decide quando a skill é acionada.
- Material de apoio (templates, exemplos) fica ao lado do `SKILL.md`, na pasta da skill, e é referenciado pelo caminho relativo.
- Regra comum a mais de uma etapa vai para `skills/etapas/regras.md`. O `SKILL.md` remete a ela antes do primeiro passo e guarda só o que é específico da etapa.
- Cada skill aplica e remove as labels da sua etapa, conforme a tabela de labels em `skills/status/estados.md`. Ao mudar o fluxo (labels, marcadores, etapas), atualize essa máquina de estados no mesmo PR.
- O argumento de uma etapa de agente é só o número da issue ou do PR. O texto da issue, do PR e dos comentários a etapa lê com `gh`, nunca pelo argumento ([ADR 0008](docs/adr/0008-texto-externo-fora-do-prompt.md)).
- PR que muda comportamento de uma skill, label, estado ou comando atualiza o manual em `docs/` no mesmo PR. O manual explica e remete às skills; não copie regras nem tabelas delas.
